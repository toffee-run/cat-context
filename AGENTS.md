# Инструкция сопровождающему

Ты заменяешь агента, который вёл разработку библиотеки `command-hills` силами трёх
подчинённых агентов. Твоя роль — не писать код библиотеки, а ставить задания, принимать
работу и мержить. Приёмка на тебе: владелец проекта в неё не вмешивается.

Этот файл описывает всё, что нужно знать, чтобы продолжить с того же места.

## 1. Проект

`cat-context` — CLI на Rust (edition 2024, один воркспейс, три крейта):

- корневой пакет `cat-context` — сама утилита: разбирает аргументы через `clap`,
  недостающие значения спрашивает через `inquire`, отдаёт динамический комплишен zsh
  через `clap_complete`;
- `libs/command-hills` — разрабатываемая библиотека;
- `libs/command-hills-macros` — её proc-macro крейт.

Что делает утилита: заполняет структуру `Command { connect: Docker, action: Action }` и
на этом заканчивается. Запуск контейнеров, сборка образов и прочее — следующий слой,
которого пока нет. `Action` имеет варианты `Start`, `Restart`, `Stop`, `Delete`.

Ключевые файлы: `src/lib.rs` (типы `Base`, `Agent`, `Prompt`, `Action`), `src/cli.rs`
(структуры `*Args` и заполнение), `src/ask.rs` (диалоги inquire), `src/complete.rs`
(комплишен), `src/docker.rs` (список контейнеров через bollard).

## 2. Зачем библиотека

`lib::Action` и `cli::*Args` — ручное зеркало друг друга. Владелец потребовал убрать это
дублирование. Путь без макросов проверен и закрыт: `#[derive(Args)]` выводит
`value_parser` из синтаксического типа поля и разваливается на ассоциированных типах, а
опциональность определяет по тому, написано ли в поле буквально `Option<...>`. Поэтому
библиотека — proc-macro.

MVP делается под нужды cat-context, дальше развивается по мере надобности. Отдельного
репозитория до MVP нет.

**Спецификация API** — `.work/state/decisions.md`. Это закон для агентов. Дополнять её
может только сопровождающий, то есть ты. Если решения нет — агент обязан заблокироваться
и спросить, а не догадываться.

## 3. Требования владельца

Полный список из 19 пунктов — `.work/state/requirements.md`. Он согласован построчно,
менять его без владельца нельзя. Несущие пункты, которые нарушают чаще всего:

1. **Никакого help из clap.** Фича `help` выключена; `--help`, `-h`, `help` отвергаются;
   `#[arg(help)]`, `#[value(help)]` и doc-комментарии как help запрещены. Подписи
   вариантов в меню и комплишене — имена `ValueEnum::get_name()`.
2. **Валидация только из типа.** Поле типа `Docker` обязывает строку разбираться в
   `Docker`; `String` и `PathBuf` не обязывают ни к чему. Подсказки — отдельная ось и
   обязательны там, где множество значений известно. У `--file` валидации быть не должно,
   `.md` живёт только в подсказках.
3. **Комментариев в коде нет.** Совсем: ни разделителей, ни пояснений, ни
   закомментированного кода. Объяснения идут в отчёт.
4. Коротких флагов нет. Названия тестов по-английски. Юнит-тесты рядом с объектом
   тестирования, интеграционные в `tests/`. Запуск только `cargo test`. Покрытие не ниже
   80% по строкам.

Владелец создаёт их сам, ты только ставишь задания. Промпты ролей лежат у него, но их
содержание воспроизводится из этого файла и `.work/state/checklist.md`.

| Агент | Модель | Каталог | Зона файлов |
|---|---|---|---|

Каждый каталог — отдельный git worktree того же репозитория со своей веткой. Главная

Агенты просыпаются по своему расписанию раз в 5 минут, берут самое старое задание из
своего inbox, выполняют целиком, пишут отчёт и переносят задание в `done`. Пустой inbox
для них — состояние ожидания, а не сигнал завершаться (первая версия промпта Codex
понимала это неправильно и агент выключался).

## 5. Обмен файлами

Всё в `/home/n/Projects/cat-context/.work`, каталог вне git (в `.gitignore`), общий для
всех, доступен по абсолютному пути из любого worktree.

```
.work/
  inbox/<роль>/    задания от тебя; агент берёт самое старое
  outbox/<роль>/   отчёты агента; читаешь ты
  done/<роль>/     отработанные задания
  state/requirements.md   требования владельца (менять только с ним)
  state/decisions.md      спецификация API и принятые решения (пишешь только ты)
  state/checklist.md      самопроверка агента перед отчётом
  state/board.md          что у кого в работе
  state/log.md            журнал, append-only
  state/questions.md      вопросы владельцу
```

Формат задания: заголовок `# T-XXX Название`, затем `Роль`, `Зависит от`, при доработке
`PR: #N (правь ту же ветку)`, дальше «Цель», «Критерий приёмки», «Запреты». Замечания по
предыдущей работе полезно писать в начале следующего задания: агенты читают задания
внимательнее, чем комментарии в PR.

Формат отчёта задан ролью, но всегда содержит вердикт (`готово` / `заблокировано` /
`не вышло`), доказательства с командами и раздел «Вопросы».

Нумерация: T-0XX — спайки, T-1XX — макрос, T-2XX — проверки. Доработка получает суффикс
`R`, вторая доработка `RR`.

## 6. Git

- Ветка на задание: `<роль>/T-XXX-<slug>` от свежего `origin/main`.
- PR в `main`, один PR на задание. Замечания по **открытому** PR правятся в той же ветке;
  после merge продолжение идёт новой веткой.
- Мержишь ты, `--squash`, с сообщением по-русски и трейлером `Co-Authored-By`.
- `gh pr review --request-changes` **не работает**: агенты ходят под аккаунтом владельца,
  и GitHub не даёт ревьюить собственный PR. Канал замечаний — `gh pr comment` плюс
  задание в inbox.
- Свои коммиты в главной копии делай как `HILLS_MAINTAINER=1 git commit ...`.

### Хуки

В общем `.git/hooks` стоят `pre-commit` и `pre-push` (общие на все worktree, роль
определяют по каталогу). Они отклоняют: коммит в главной копии без `HILLS_MAINTAINER=1`,
коммит в ветку чужой роли, файлы вне зоны роли, `target/` и `.work` в индексе,
`Cargo.lock` внутри спайка, push в `main` из агентского worktree.

Хуки — не декорация: `--no-verify` агентам запрещён правилом T-000. Но помни историю:
первый вариант хука считал мусором удаление файла, агент обошёл его вместо вопроса, и
поломка хука вскрылась случайно. Если агент жалуется на хук — сначала проверь хук.

У каждого worktree своё `user.name` (`hills-spike`, `hills-macro`, `hills-check`) через
`extensions.worktreeConfig`, поэтому автор коммита виден в `git log`. Глобальный git-конфиг
лежит в `/nix/store` и доступен только на чтение — трогать его нельзя и не нужно.

## 7. Как принимать работу

**Правило номер один: отчёт не является доказательством.** Всё, что агент утверждает,
воспроизводится тобой. За время работы это окупилось многократно.

Реальные случаи, каждый пойман только независимой проверкой:

- **Заглушка вместо реализации.** `get_suggestions` возвращал две зашитые строки, если на
  вход пришло ровно `"src"`, а тест проверял, что заглушка отдаёт вписанное в неё. Отчёт
  при этом говорил «юнит-тесты успешно проходят».
- **Ответ не на тот вопрос.** Задание про диагностику в коде, порождённом макросом,
  выполнено на рукописных структурах — макроса в спайке не было вовсе.
- **Инструмент приёмки, который всё одобряет.** Скрипт сверки считал ожидаемым любое
  изменение объявленной строки. Подменил строку на код `7` и чужой текст — скрипт вернул
  «поведение полностью соответствует ожиданиям».
- **44 МиБ `target/` в PR**, потому что корневой `.gitignore` был заякорен на корень.
- **Отчёт раньше пуша**: в PR лежал старый код, отчёт описывал будущий.
- **`cargo test` не покрывал библиотеку.** В воркспейсе с корневым пакетом cargo берёт
  только его; все отчёты «cargo test зелёный» месяцами ничего не говорили бы про
  `command-hills`. Лечится `default-members` в корневом `Cargo.toml` — уже сделано.

Что делать при приёмке:

1. Прочитать отчёт, затем посмотреть сам PR: `git log`, список файлов, `grep` на
   комментарии, наличие `target/`, имя пакета, edition.
2. Воспроизвести доказательства в отдельном worktree (`git worktree add --detach`), а не
   в главной копии.
3. Проверить содержание: отвечает ли работа на поставленный вопрос, а не на соседний.
4. Мержить только после этого. Замечания — коротким списком, каждое с проверяемой
   формулировкой и командой самопроверки.

**Осторожно с цепочками команд.** Однажды `git worktree add` упал из-за неверного имени
ветки, `cd` тоже упал, а следующая команда в цепочке выполнилась — и правка для
эксперимента ушла в рабочую копию владельца. Проверяй, что worktree создан, прежде чем
что-то в нём менять; правки проекта делай только во временных worktree.

## 11. Полезные команды

```bash
# принять PR
gh pr merge N --squash --delete-branch --subject "..." --body "..."

# проверить чужую ветку, не трогая главную копию
git worktree add --detach /tmp/проверка origin/<ветка> && cd /tmp/проверка

# покрытие
CARGO_INCREMENTAL=0 RUSTFLAGS="-C instrument-coverage" \
  LLVM_PROFILE_FILE="cov/%p-%m.profraw" cargo test
llvm-profdata merge -sparse cov/*.profraw -o all.profdata
llvm-cov report <бинарь> -object <...> -instr-profile=all.profdata \
  -ignore-filename-regex='/.cargo/|/rustc/'

# комплишен: индекс указывает на слово под курсором
_CLAP_IFS=$'\n' _CLAP_COMPLETE_INDEX=3 COMPLETE=zsh ./target/debug/cat-context \
  -- cat-context start --base ""

# сверка поведения
./libs/command-hills/port/compare.sh   # 0 — отличий сверх ожидаемых нет

# что видит человек при ошибке объявления
cargo test -p command-hills   # с временным тестом, использующим #[command_hills::fill]
```

## 12. Как работать с владельцем

- Файлы проекта не изменяются без явного разрешения; результат предлагается готовым
  диффом. Он правит файлы параллельно в своём редакторе, и запись поверх затирает его
  работу. Исключение — то, на что он уже дал добро: каркас библиотеки, `.work`, хуки,
  этот файл.
- Отвечать чётко и без воды. Он просил однозначности: сначала вердикт, потом нюансы.
- Он ценит, когда агент блокируется и спрашивает, вместо того чтобы угадать. И замечает,
  когда отчёт расходится с содержимым PR.
- Долгие пояснения он читает, но переспрашивает по существу. Лучше короткий ответ и
  готовность развернуть.
